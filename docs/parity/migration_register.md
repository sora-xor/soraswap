# SoraSwap Migration Register

This register tracks behavior-level coverage from the reference implementation in this Kotodama repo.

Status values:
- `stub` - repo placeholder only
- `adapted` - intermediate Kotodama shape exists, but the module is not release-eligible and must be resolved to `ported`
- `ported` - intended behavior is present in this repo with executable local acceptance and matching interface/state docs; the release checklist separately requires current-chain Taira or production evidence before any public deployment claim
- `blocked` - excluded from the production claim until the named `../iroha` capability or acceptance gap is closed; `make release-checklist` fails while any row remains `blocked`
- `reference-only` - kept for comparison, not part of the deployable surface

## Release Guardrails And Deferred Scope
- DLMM helper/NFT wrappers are outside the first-release SoraSwap production surface. The release-eligible LP position surface is the current `position_id`-keyed Kotodama accounting until a Sora Nexus helper/NFT requirement is accepted into scope.
- Conflict-aware state layout docs, public entrypoint specs, generated interface docs, and deploy-time contract snapshots are maintained under `docs/state_layouts/`, `docs/interface_specs/`, and `deployments/<env>/contracts.*.json`; the release gate requires the target-chain snapshots before any production claim.
- The sibling `../iroha` current contract-deploy, typed-view, trigger, and universal-dataspace asset APIs remain release dependencies across codegen, host/runtime dispatch, Torii normalization, and CLI helpers.
- The bridge production claim stays tied to the proof-authority Taira path; direct raw-input `finalize_inbound(...)` debug calls cannot be release evidence because non-authority callers are rejected on chain.
- The parallel production deployment family remains gated behind the Taira artifact set, smoke evidence, and contract-console proof evidence being green with the exact same evidence layout.
- Perps, options, and cover each have independent custody/accounting invariants and are all required by the full-scope acceptance checklist.
